Loading a serialized object can no longer trigger code execution, including payloads sent to and returned by SpeQtrum. `deserialize` and `deserialize_from` now only rebuild built-in types, NumPy arrays and scalars with numeric or boolean dtypes, SciPy CSR matrices, and classes registered with `@yaml.register_class`. They never import modules named in the payload, and `!!python/...` tags are rejected, except for the enum values written by previous versions, which still load. The loader does not limit payload size.

As part of this change, functions and lambdas can no longer be serialized, and the `dill` dependency has been removed. Serializing a callable now raises a `SerializationError`, and loading an old payload that contains a pickled function (`!function` / `!lambda`) raises a `DeserializationError`. Schedules built with callable coefficients are unaffected, since those callables are turned into symbolic expressions when the schedule is created.

Any class that needs to be serialized, including custom subclasses of QiliSDK classes such as `Function`, `ExperimentFunctional` or `ExperimentResult`, must now be registered with `@yaml.register_class`. For example:

```python
from qilisdk.experiments import ExperimentFunctional, ExperimentResult
from qilisdk.utils.serialization import deserialize, serialize
from qilisdk.yaml import yaml


@yaml.register_class
class MyExperimentResult(ExperimentResult):
    plot_title = "My Experiment"


@yaml.register_class
class MyExperiment(ExperimentFunctional[MyExperimentResult]):
    result_type = MyExperimentResult


experiment = deserialize(serialize(MyExperiment(qubit=0, averages=100)), MyExperiment)
```

Registering two classes with the same name now raises a `ValueError`, since they would share a YAML tag. Arrays and NumPy scalars with other dtypes (strings, objects, dates) now fail when serialized, instead of producing a file that cannot be loaded back.
